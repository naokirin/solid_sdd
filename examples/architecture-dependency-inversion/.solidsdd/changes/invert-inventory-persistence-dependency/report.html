2. 機能要件

ゴール

Inventory の永続化技術を、ドメインモジュールを変更せずに交換（またはテストでモック化）できるようにする。具体的な実装ではなく抽象に依存させることでこれを実現する。

スコープ内 (in_scope)

  • R1 — inventory_repository_port を導入する。直接的な inventory -> postgres_store 依存を取り除き、代わりに inventory -> port と postgres_store -> port を追加する
  • R2 — postgres_store が inventory に直接依存できないようにし、port にのみ依存できる forbid_dependency 制約を追加する

スコープ外 (out_of_scope)

  • X1 — src/ での実装。本サンプル全体が構造設計の成果物であり、実行可能なプロジェクトではない
  • X2 — 2つ目の永続化アダプタの導入。反転を示すには実装（PostgresInventoryStore）1つで十分

成功基準

  • SC1 — ArchitecturePlan が inventory_repository_port、inventory -> port / postgres_store -> port の依存関係、postgres_store -> inventory の forbid_dependency 制約を記録し、solidsdd-lint / critique(architecture_plan) を通過すること

受入シナリオ（Gherkin）

ArchitecturePlan — 実施済

status: changed

本 change は、このサンプルの先行 change establish-inventory-persistence が確立した依存関係を反転させます：

Before:  Inventory -> PostgresInventoryStore
After:   Inventory -> InventoryRepositoryPort <- PostgresInventoryStore

モジュール

id責務ownspublic
inventorySKU ごとの在庫を所有し、在庫の読み取り・増減操作を公開するStockInventoryService
inventory-repository-portInventory が依存し、インフラ側のアダプタが実装する永続化の抽象——
postgres-store在庫レコードの具体的な PostgreSQL 永続化——

依存関係

fromto理由kind
inventoryinventory-repository-port永続化ポート経由で在庫を読み書きするruntime
postgres-storeinventory-repository-portPostgreSQL で永続化ポートを実装するdata

構造上の制約

typefromto理由
forbid_dependencypostgres-storeinventoryインフラは永続化ポートのみに依存し、Inventory ドメインモジュールに直接依存してはならない。これにより、ドメイン側が知ることなく永続化実装を交換できる。

理由

architecture-reasoning.md より：port は inventory にネストさせず、独立したトップレベルの softwareSystem（inventory の兄弟要素）としてモデル化しています。Structurizr は親要素とその子要素の間の relationship を禁止しているためです。これは本例の作成中に実際の Structurizr CLI で確認し、scripts/solidsdd-architecture/validate.py でも同様に検証しています。

Critique (architecture_plan) — pass

指摘なし。依存方向が明確な理由とともに実際に反転している。取り除かれた inventory -> postgres_store エッジは（新しい forbid_dependency 制約により）暗黙に復活しない。port は親子関係を正しく回避している。

6. 判断とトレードオフ

  • inventory_repository_port を（ネストした container ではなく）兄弟の softwareSystem として導入。inventory と postgres_store の両方からの relationship の対象になれるようにし、Structurizr の親子関係ルール違反を回避する
  • forbid_dependency: postgres_store -> inventory を追加し、本 change で取り除いた直接結合が後から静かに復活しないようにする
  • port 1つ・ホップ1つ分のコストを許容する（この最小サンプルでは永続化技術は1つのみ）— このトレードオフは、永続化の交換やテスト容易性が実際に重要になる場合にのみ価値がある
  • 検討して却下した代替案：直接依存を維持したまま実際の Postgres インスタンスに対するテストのみを追加する案 — 結合のコストを取り除くのではなく隠すだけになるため却下した
